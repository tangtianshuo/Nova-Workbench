## Surface Contracts

### Surface 1: ChatPanel 记忆候选确认卡片 (MEM-01/02/03)

**Location:** `src/components/ChatPanel.tsx`, rendered in `DrawerBody` after `pendingDestructiveAction`, before `bottomRef`.

**Structure — clone of the knowledge-write banner (ChatPanel.tsx:383-396):**

```tsx
{pendingMemory && (
  <div className="rounded-[var(--radius-lg)] border border-accent/30 bg-accent-subtle px-3.5 py-3 text-sm text-text-primary">
    <div className="font-medium">待确认的记忆</div>
    <div className="mt-1 text-xs text-text-secondary">{pendingMemory.content}</div>
    <div className="mt-1 text-xs text-text-tertiary">来源: 本次对话 · {candidateOrigin}</div>
    <div className="mt-2 flex gap-2">
      <Button type="button" variant="primary" size="sm" onClick={confirm} disabled={loading}>记住</Button>
      <Button type="button" variant="secondary" size="sm" onClick={reject} disabled={loading}>忽略</Button>
    </div>
  </div>
)}
```

**Interaction contract:**
- One card visible at a time (queue head). Confirm/ignore resolves it; next candidate (if any) renders in the same slot. Matches Phase 14 "latest one banner" precedent — no stacked list.
- Both buttons `disabled={loading}`.
- Restore behavior: on session restore, pending memory candidates re-appear (same as `pendingKnowledgeWrites` restore in ChatPanel.tsx:124-127). Rejected candidates never re-render (MEM-02).
- Candidate origin line distinguishes: `来源: 本次对话` (model-inferred) vs `来源: 你的指令` (user said "记住") — text only, no visual difference (both require explicit confirm; locked decision: model inference can only create candidates).
- No expiry countdown UI. Expiry (7d) and queue cap (~20) are backend behavior; the card shows nothing about them. If the queue is full the UI is simply unaware — no "queue almost full" affordance (YAGNI, Phase 17 morning report will surface pending candidates).

### Surface 2: KnowledgeBaseView 搜索 + 过滤 (MEM-06/07)

**Location:** `src/views/KnowledgeBaseView.tsx` sidebar (w-64 column). Existing static `Input` at :100-105 becomes the live FTS5 query box.

**Layout (top to bottom in sidebar):**

1. **Search input** (existing shell, now functional): `Input` with `MagnifyingGlass` icon, `placeholder="搜索文档..."`. Debounce 300ms. Query >= 1 char triggers search (2-char Chinese like "需求" must hit — CJK per-char segmentation is backend's job, not UI's).
2. **Filter row** (visible always, not only during search): three compact controls stacked vertically, `gap-2`:
   - `Select` 标签 (categories, existing `categories` memo) — placeholder "全部标签"
   - `Select` 产品 (`products` from productStore) — placeholder "全部产品"
   - `Select` 时间 ("全部时间" / "最近 7 天" / "最近 30 天") — placeholder "全部时间"
   Each `Select` sized to sidebar width, `h-8` trigger.
3. **Result / tree area** — two modes:
   - **Browse mode** (empty query): existing category tree, unchanged.
   - **Search mode** (query or any filter active): flat result list replaces the tree. Each row:
     ```tsx
     <button className="w-full flex flex-col gap-0.5 px-3 py-2 rounded-[var(--radius-sm)] text-sm text-text-secondary hover:bg-bg-secondary text-left">
       <span className="truncate font-medium text-text-primary">{item.title}</span>
       <span className="text-xs text-text-tertiary">{productName} · v{version} · {updatedAt}</span>
     </button>
     ```
     Clicking a row selects the document in the existing viewer (same `setActiveItemId` flow).
4. **Mode toggle:** when in search mode, a small "清除" ghost button (`Button variant="ghost" size="sm"`, text "清除筛选") appears at the top of the result list; clears query + all three filters, returns to tree.

**Result count line:** above results, `text-xs text-text-tertiary`: `{n} 条结果`. 

**No-search-state behavior:** filters alone (no query) also trigger search mode — structured filtering works without keywords (MEM-06: 关键词+结构过滤混合).

### Surface 3: 最小记忆管理列表 (查看 + 删除) 

**Location:** `src/views/KnowledgeBaseView.tsx` — new "长期记忆" entry in the existing sidebar "快速访问" section (alongside 我的收藏/所有文档), with `Brain` icon (`size={16} weight="duotone" className="text-accent"`). Clicking it swaps the main pane from document viewer to the memory list. No new route, no new view file — a boolean pane state (`activePane: 'docs' | 'memories'`) in the existing component.

**This is a Claude's-discretion placement** (CONTEXT.md locks "最小列表(查看+删除)" but not location). KnowledgeBaseView reuse chosen over a new SettingsView section because: memories are knowledge-domain, the view already has sidebar+pane chrome, and zero new routing is needed.

**Memory list pane structure:**

```
┌─ Header (h-12, matches existing viewer header) ──────────────┐
│ 长期记忆 · N 条                    [删除全部 variant="ghost"] │  ← 删除全部: OUT OF SCOPE, do not build
└──────────────────────────────────────────────────────────────┘
[ memory card ]  × N  (space-y-2, p-10 scroll area, max-w-2xl mx-auto — matches doc viewer)

Memory card:
<Card className="p-4">
  <div className="flex items-start justify-between gap-2">
    <p className="text-sm text-text-primary leading-6">{memory.content}</p>
    <Button variant="ghost" size="sm" onClick={askDelete}>删除</Button>
  </div>
  <div className="mt-2 flex items-center gap-2 text-xs text-text-tertiary">
    <Badge variant="neutral">{scopeLabel}</Badge>
    <span>确认于 {confirmedAt}</span>
    {supersededBy && <Badge variant="warning">已被取代</Badge>}
  </div>
</Card>
```

**Interaction contract:**
- View + delete ONLY. No edit button, no add button (locked: 无编辑).
- Delete is per-item, destructive: opens existing `Dialog` (`max-w-md`) — copy in Copywriting Contract below. Confirm = `Button variant="danger"` "删除记忆", cancel = `variant="secondary"` "取消".
- Superseded memories (MEM-05 supersedes chain): visible in the list, marked with `Badge variant="warning"` 已被取代, still deletable. History is auditable — do NOT hide or filter them out in v1.
- Version/scope metadata comes from the memory record's source fields (MEM-07); if a field is absent, omit the element rather than render a placeholder.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (memory confirm) | **记住** (confirm button on chat card) |
| Secondary CTA (memory reject) | **忽略** (reject button on chat card) |
| Card title | 待确认的记忆 |
| Card origin line | 来源: 本次对话 · {时间} / 来源: 你的指令 · {时间} |
| Search placeholder | 搜索文档... (unchanged, existing) |
| Filter placeholders | 全部标签 / 全部产品 / 全部时间 |
| Clear filters | 清除筛选 |
| Result count | {n} 条结果 |
| Search empty heading | 没有匹配的文档 |
| Search empty body | 换个关键词试试,或清除筛选条件查看全部文档。 |
| Memory list empty heading | 还没有长期记忆 |
| Memory list empty body | 在对话中让 AI 记住你的偏好和工作习惯,确认后会出现在这里。 |
| Error state (search/confirm 失败) | 检索失败,请稍后重试;若持续失败请重启应用。 (toast via `useToast()`, type: 'error') |
| Destructive: 删除记忆 | Dialog title: 删除这条记忆? body: 删除后 AI 将不再使用这条信息,且无法恢复。 confirm: 删除记忆 (danger) / 取消 |

**Toast feedback:** memory confirm → `toast({ type: 'success', title: '已记住' })`; reject → silent (no toast, ignoring is lightweight); delete → `toast({ type: 'success', title: '记忆已删除' })`.

## Context Injection Visibility (MEM-08)

No dedicated UI. `context_injected` events are audit-log artifacts, not user-facing. The existing `ToolTrace` in ChatPanel continues to show tool activity; FTS5 auto-injection per turn is NOT surfaced as a visible element (silent retrieval, no banner, no badge). Rationale: injection happens every turn — surfacing it would be noise. Auditing goes through the event log (Phase 13/14 tooling), not the chat UI.
