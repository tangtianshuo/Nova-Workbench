## Surface Contracts

### Surface 1: ChatPanel PRD 草稿确认卡片 (DELIV-01)

**Location:** `src/components/ChatPanel.tsx`, rendered in `DrawerBody` alongside `pendingMemory` (after `pendingDestructiveAction`, before `autoRemembered`/`bottomRef`). New state + refresh pattern mirrors `refreshMemoryCards` (ChatPanel.tsx:114-130); refresh triggered in `onToolEnd` when `name === 'generateDeliverable'`.

**Structure — clone of the memory card (ChatPanel.tsx:483-493) with a draft preview added:**

```tsx
{pendingPrdDraft && (
  <div className="rounded-[var(--radius-lg)] border border-accent/30 bg-accent-subtle px-3.5 py-3 text-sm text-text-primary">
    <div className="font-medium">待确认的 PRD 草稿</div>
    <div className="mt-1 text-xs text-text-secondary">产品: {productName}</div>
    <div className="mt-1 text-xs text-text-secondary line-clamp-3 whitespace-pre-wrap">{pendingPrdDraft.draft}</div>
    <div className="mt-1 text-xs text-text-tertiary">来源: 本次对话 · {formatTime(pendingPrdDraft.createdAt)}</div>
    <div className="mt-2 flex gap-2">
      <Button type="button" variant="primary" size="sm" onClick={openEditor} disabled={busy}>确认并编辑</Button>
      <Button type="button" variant="secondary" size="sm" onClick={rejectDraft} disabled={busy}>忽略</Button>
    </div>
  </div>
)}
```

**Interaction contract:**
- Draft preview is plain text (`whitespace-pre-wrap line-clamp-3`) — no markdown rendering in the card; full rendering happens in the editor (Surface 2). The card shows enough to recognize the draft, not to read it.
- "确认并编辑" opens the PRD edit Dialog (Surface 2). The card REMAINS visible until 落槽 succeeds or the candidate is ignored — closing/cancelling the Dialog must never lose the draft (Phase 14 restore semantics).
- "忽略" = reject candidate: card disappears, rejection recorded and injected into system prompt for anti-repeat (MEM-02 pattern, locked decision). Silent — no toast (Phase 15 reject precedent).
- One card at a time (queue head), same as Phase 15 memory card. `paramsHash` dedup means the same draft never re-queues.
- Crash/restore: pending PRD candidate re-appears after restart (Phase 14 confirmationStore persistence — same restore path as `pendingKnowledgeWrites`, ChatPanel.tsx:152-155).
- "未选产品" never reaches the card: `generateDeliverable` tool errors before a candidate exists (tool carries `uiStore.selectedProductId` context; locked decision). Error surfaces in the existing `ToolTrace` as 失败 + error copy below.

### Surface 2: PRD 编辑 Dialog (DELIV-02)

**Location:** new component (e.g. `src/components/PrdDraftDialog.tsx` — exact file split is executor discretion) opened from the Surface 1 card. Does NOT navigate to 研发中心 (locked decision: 编辑器入口在 ChatPanel 卡片,不跳转).

**Structure:**

```tsx
<Dialog open={isOpen} onOpenChange={setIsOpen}>
  <DialogContent className="max-w-3xl">
    <DialogHeader
      title={draft.title /* PRD 标题, from candidate */}
      description={`${productName} · 编辑后落槽至研发中心,并同步知识库索引`}
    />
    <MarkdownEditor
      value={editedDraft}
      onChange={setEditedDraft}
      minHeight="320px"
    />
    <DialogFooter>
      <Button variant="secondary" onClick={close} disabled={busy}>取消</Button>
      <Button variant="primary" onClick={commitToSlot} loading={busy}>落槽至研发中心</Button>
    </DialogFooter>
  </DialogContent>
</Dialog>
```

**Interaction contract:**
- Prefilled with the candidate draft; user edits freely (full MDXEditor toolbar, already lazy-loaded via the `MarkdownEditor` wrapper).
- **"落槽" is the ONLY confirmation-consume point** (atomic consume + write, same two-phase shape as `handleConfirmKnowledgeWrite`). Rationale: the card's "确认并编辑" expresses intent to review, but consuming there would orphan the candidate if the user cancels the editor — consume-at-落槽 keeps cancel lossless. This is the UI-level reading of the locked 确认→编辑→落槽 order.
- "取消" / dialog X: close only. Candidate stays pending; card still in ChatPanel; reopening the dialog restores the ORIGINAL draft (edits made in a cancelled session are not persisted — the candidate is the source of truth until 落槽).
- 落槽 onto an occupied slot = new version supersede (version chain preserves history, MEM-04 pattern). NOT a destructive action — no confirmation dialog, no danger styling (locked decision: 非覆盖删除).
- Success: close Dialog, remove card, append assistant message, success toast (copy below). FTS5 同事务索引 means no "indexing..." intermediate state — the toast fires when the write returns (DELIV-04 is invisible to the UI by design).
- Failure: Dialog stays open, `busy` resets, error toast; draft and card intact for retry.
- `busy` state: 落槽 button `loading`, both footer buttons disabled.

### Surface 3: 研发中心卡槽 AI 溯源徽章 (DELIV-03)

**Location:** `src/components/product/FullDeliverablesTab.tsx` deliverable card badge row (:278-286), left group, after the phase badge (`<Badge variant="accent">{d.phaseName}</Badge>`). `Sparkle` is already imported there (:11).

**Structure:**

```tsx
{d.aiSource && (
  <Tooltip content={`AI 生成 · ${formatDateTime(d.aiSource.generatedAt)} · 会话 ${d.aiSource.sessionId.slice(0, 8)}`}>
    <Badge variant="accent">
      <Sparkle size={12} weight="fill" />
      AI
    </Badge>
  </Tooltip>
)}
```

**Interaction contract:**
- Rendered ONLY when the slot's current version has AI provenance (source: 'agent' — fields per CONTEXT: session_id + event_id + generated_at). Mock/manual deliverables render nothing (DELIV-03 is about marking agent-sourced content, not decorating everything).
- Tooltip shows 生成时间 + 会话 ID (short, first 8 chars — full UUID is noise; event_id stays in the event log, not the tooltip). `side="top"` default; `TooltipProvider` already wraps the app.
- Non-interactive beyond hover — the badge is provenance display, not a link. No click-through to the session (v2 UX-05 territory, out of scope).
- Badge + tooltip carry the full contract; the deliverable preview Dialog (:366) is NOT modified this phase.

### Surface 4: KnowledgeBaseView (DELIV-04) — ZERO UI CHANGES

Explicitly out of contract for new UI (locked decision). Evidence it needs nothing:
- Sidebar category list is derived dynamically from data (`KnowledgeBaseView.tsx:38-48` useMemo) — a doc landing with `category: 'deliverable'` appears automatically.
- FTS5 hit flows through the existing search + filter surfaces (Phase 15 spec, unchanged).
- The only data contract: PRD lands as knowledge doc with `category: 'deliverable'` + `tag: 'prd'` + product association. Do not add a hardcoded category, a badge, or a special row — the planner enforces this at the write API, not the view.
