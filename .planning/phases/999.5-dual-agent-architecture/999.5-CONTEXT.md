# Phase 999.5: 双 Agent 架构 — 日常助手 + 产研 coding Agent - Context

**Gathered:** 2026-08-31
**Status:** Ready for planning(BACKLOG — 归位 v0.4 系,promote 前需补排期裁定)

<domain>
## Phase Boundary

设计 Nova 的双 Agent 形态:① 日常 AI 助手(日程分发、任务管理、轻量日常工作);② 产研中心 coding Agent(真实代码工作)。裁定二者与 ADR-0004(subagent-as-tool)、现有 Rust run engine(ADR-0003)的关系,以及从 Oh my pi(omp)借鉴的清单。本 phase 是架构决策捕获,不是实施 phase;实施随 v0.4(依赖 PM CRUD 工具立项等前置)。

</domain>

<decisions>
## Implementation Decisions

### 双 Agent 形态(Area 1)
- **D-01:** 双入口 persona + spawn 互通。两个产品入口(聊天侧栏助手 / 产研中心 coding),同一 Rust 引擎上的两个 persona manifest,形状复用 ADR-0004 manifest(name/description/systemPrompt/toolWhitelist)。助手可 spawn coding 子代理(spawn_subagent);不设 router,主 agent 即入口。
- **D-02:** 会话形态 = 对话式工作台 + tab-run 共存。聊天是助手主入口;产研 tab-run(Phase 26 形态)是 coding 场景既有入口,二者共享引擎与事件模型,不合并也不互斥。
- **D-03:** 会话列表 = 共享会话列表 + persona 徽章。不拆两个列表;tab-run 已用独立 sessionId 隔离(Phase 26),persona 只是标注维度。
- **D-04:** ADR-0004 需补边界注记:产品入口层 persona ≠ run 内固定角色编排,与"否定 router"裁定不冲突。落点 = ADR-0004 文档补一段,随 v0.4 实施时写。

### omp 复用策略(Area 2)
- **D-05:** 语义移植 + crates 评估,sidecar 否决。loop 留 Rust 引擎(ADR-0003 引擎即 omp 级语义的 Rust 实现);v0.4 coding 增量 = 5 工具(read/write/edit str-replace/exec/grep)+ diff 审批卡 + exec 白名单(既有裁定不变)。
- **D-06:** sidecar(omp --mode rpc)作为产品架构**否决**。理由:① 真相源分裂 — omp run 不落 agent_events,parity 锁/审计/崩溃恢复/托盘常驻语义全部断链("无事件日志不接 MCP"原则同样适用);② 调度旁路 — 双队列交互优先/cap-3/取消级联对 sidecar run 失效;③ HITL 语义降级 — extension_ui_request 是易失对话帧,对不上持久化确认队列;④ 密钥出主进程;⑤ Bun ≥1.3.14 分发负担 + omp 产物以 win32-x64 为主与三平台目标冲突;战略时机:v0.3.2 刚 shipped,把最高强度工作负载移出刚建成的引擎 = 自我否定。
- **D-07:** 立项时加 research 任务:评估 omp 的 Rust 原语 crate(pi-walker / pi-ast / grep / diff)与 pi-natives N-API cdylib 的可分离性,可直接进 Cargo 依赖的走 vendoring。注意事实:omp 的 agent 核心是 TS harness(@oh-my-pi/pi-agent-core 等),Rust 部分是 N-API 性能原语(~80k 行 natives + ~80k vendored),**loop 层没有 Rust 可移植**——旧记忆"omp 核心约 8 万行 Rust"已修正。

### 助手自主性/触发机制(Area 3)
- **D-08:** ②档起步:被动 chat + 定时/事件触发的系统 run。Rust 侧小触发器(定时器/日程事件/启动钩子)→ **先做本地零-LLM 检查**(SQL 查逾期任务/今日日程),有值得说的事才升级为 LLM run。产物走 notify.rs 系统通知 + HITL 卡。自主性 ≠ 持续 API 开销。
- **D-09:** 触发 run 在事件中标注发起方(system vs user),审计需要。
- **D-10:** 不做常驻 agent 进程(与 run-based 有界模型相克)。③档(后台观察 + 自主行动,如自动建任务/改期)写进 v0.5+ 演进方向,触发条件库渐进丰富。

### 助手工具面与 HITL(Area 4)
- **D-11:** PM CRUD 工具原生化单独立项(v0.4 前置小 phase:task_*/schedule_* 原生工具 + 风险标注)。该依赖不在 v0.3.3 圈定范围内,须在依赖它的 v0.4 助手/coding 场景前补立项。v1 助手工具包 = task_* + schedule_* + knowledge_search(FTS5)+ 工作区文档读取 + 交付物生成入口(复用 Phase 16 管线)。
- **D-12:** 助手侧 HITL = 三档风险档案:读操作免确认 → 可逆轻写(建任务/勾完成/调日程)白名单免确认 → 删除/批量/exec/系统通知确认。coding 侧维持严格 diff 审批(write/edit 一律 diff 卡,exec 白名单)。一套机制(确认队列 + 工具风险标注),两套策略。会话级信任开关后续可叠加,不在首批。

### omp 借鉴清单复评(Area 5)
- **D-13:** 全盘确认旧裁定:hashline 维持 v0.5(v0.4 用 str-replace + old_string 唯一性校验 + 失败回带行号;v0.5 立项时协议照抄 omp 的 stale-anchor 写前拒绝语义);exec 不嵌 bash;advisor v0.4 可选;`://` scheme 记模式不做(工具注册表设计时留一句);task subagents = ADR-0004 spawn_subagent;LSP/DAP 超范围。
- **D-14:** 新增两条轻量裁定:persona manifest 加 `modelHint` 字段(助手=快模型,coding=强模型),不做 omp 的 10 角色系统,模型选择逻辑留引擎;ask tool(结构化追问)记为 HITL 轻量卡形态候选,随双 agent 实施时再定去留。stream rules 不另立(对应物 = Skill 系统 999.2);memory tools 不做(第二大脑已覆盖)。

### Claude's Discretion
- 触发器调度实现细节(cron 语义 vs 简单间隔,Phase 级决定)
- 三档风险档案的工具逐项归类表(实施时随工具定义逐个标注)
- persona manifest 的具体 schema 字段名(v0.4 与 Skill manifest 同形时统一)

</decisions>

<specifics>
## Specific Ideas

- "帮我安排今天"不能变成确认地狱 — 助手侧低摩擦是产品体验要求,不是偷懒
- 助手的主动价值 = "早上自动给日程预览/逾期提醒,不用记着问" — 这是选 ②档而不是纯被动的动因
- sidecar 讨论中的反例锚点:"如果 Nova 定位是对标 Cursor 的 coding IDE,sidecar 才成立;Nova 是 PM 工作台,coding 是 pipeline 一环"

</specifics>
