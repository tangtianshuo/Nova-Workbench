## ADR-001: 采用混合架构（本地优先 + 云端 LLM API）

**日期:** 2026-08-07  
**状态:** ✅ 已接受

### 背景

Nova PM Workspace 作为产品经理工作台，需要处理敏感的产品文档、PRD、代码等数据。需要确定数据存储和 LLM 调用的架构模式。

### 决策

采用**混合架构**：
- 所有敏感数据（产品文档、PRD、代码、对话历史）存储在用户本地
- LLM API 调用走云端（Anthropic/OpenAI/Gemini）
- 向量检索在本地执行

### 理由

1. **数据主权** — 产品经理的工作内容高度敏感，必须本地存储
2. **合规性** — 企业环境对数据外流有严格限制
3. **离线能力** — 部分功能（知识检索）可离线使用
4. **成本控制** — LLM 调用按需付费，不存储大量数据在云端

### 后果

- ✅ 用户数据安全有保障
- ✅ 满足企业合规要求
- ⚠️ 需要设计本地存储方案（SQLite + LanceDB）
- ⚠️ 需要考虑离线降级策略

## ADR-002: 采用 GraphFlow 作为工作流引擎

**日期:** 2026-08-07  
**状态:** ✅ 已接受

### 背景

PM Pipeline 需要一个工作流引擎来实现需求→PRD→原型→代码的自动化生成，并支持 Human-in-the-Loop（人工确认）。

### 候选方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| LangGraph (Node.js) | 生态成熟，HITL 原生 | 需要 sidecar，资源开销 |
| ZeroClaw | 极致轻量，Rust 原生 | HITL 能力不明确 |
| Claude Agent SDK | 开箱即用 | 模型绑定，灵活性差 |
| **GraphFlow** | **Rust 原生，HITL，Rig 集成** | 相对较新 |
| Juncture | LangGraph 完全兼容 | LLM 集成需自行处理 |

### 决策

选择 **GraphFlow** (`graph-flow` crate)

### 理由

1. **Rust 原生** — 可直接嵌入 Tauri，避免 Node.js sidecar
2. **HITL 支持** — 内置 interrupt 机制，满足人工确认需求
3. **Rig 集成** — 与 Rig LLM 库无缝集成，省去集成工作
4. **生产验证** — v1.4.2 达到 99.99% 可用性
5. **类型安全** — 编译时工作流验证

### 后果

- ✅ 零 sidecar 架构，资源占用最小化
- ✅ 全 Rust 技术栈统一
- ✅ HITL 能力完整
- ⚠️ GraphFlow 相对较新，社区较小
- ⚠️ 文档可能不完善，需要自行探索

### 备选方案

如果 GraphFlow 不满足需求，可切换到：
- **Juncture** — LangGraph 的 Rust 实现，API 兼容
- **自研** — 基于 Rust 状态机库自行实现

## ADR-003: 采用 Rig 作为 LLM 集成层

**日期:** 2026-08-07  
**状态:** ✅ 已接受

### 背景

需要选择一个 LLM 调用库，支持多 Provider（Claude、GPT、Gemini、本地模型）。

### 决策

选择 **Rig** (`rig` crate)

### 理由

1. **GraphFlow 已集成** — 无需额外集成工作
2. **多 Provider 支持** — Anthropic、OpenAI、Google、Ollama 等
3. **流式响应内置** — 聊天体验流畅
4. **类型安全** — Rust 强类型保证
5. **轻量** — 比 LangChain Rust 更简洁

### 后果

- ✅ 多 LLM Provider 灵活切换
- ✅ 流式响应支持
- ✅ 与 GraphFlow 无缝配合
- ⚠️ 某些高级功能可能需要自行扩展

## ADR-004: 采用 LanceDB 作为向量检索方案

**日期:** 2026-08-07  
**状态:** ✅ 已接受（待最终确认）

### 背景

「第二大脑」功能需要语义检索能力，需要选择向量数据库。

### 候选方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| ChromaDB (HTTP) | 功能完整 | 需要 Python sidecar |
| Qdrant | 高性能 | 需要独立服务 |
| SQLite-vec | 轻量 | 功能受限 |
| **LanceDB** | 嵌入式，零配置 | 生态较新 |

### 决策

选择 **LanceDB**

### 理由

1. **嵌入式** — 无需独立服务，直接集成到 Tauri
2. **零配置** — 开箱即用
3. **磁盘持久化** — 数据存储在本地文件
4. **性能足够** — 个人知识库规模（几万到几十万文档）
5. **Rust 支持** — 有 Rust 客户端

### 后果

- ✅ 零配置，集成简单
- ✅ 本地存储，符合数据主权
- ⚠️ 生态较新，高级功能可能缺失
- ⚠️ 如果规模超出嵌入式能力，可能需要切换

### 备选方案

如果 LanceDB 不满足需求，可切换到：
- **SQLite-vec** — 更轻量，但功能受限
- **Qdrant (嵌入式模式)** — 性能更强

## ADR-005: 采用零 Sidecar 架构

**日期:** 2026-08-07  
**状态:** ✅ 已接受

### 背景

需要确定是否在 Tauri 应用中使用 sidecar 进程（如 Node.js 运行 LangGraph）。

### 决策

采用**零 Sidecar 架构**：所有后端逻辑在 Tauri Rust 进程中执行。

### 理由

1. **资源效率** — 避免额外进程开销（Node.js 约 50-100MB）
2. **启动速度** — 单进程启动更快
3. **部署简单** — 无需管理多个进程
4. **Rust 生态成熟** — GraphFlow + Rig 满足需求

### 后果

- ✅ 资源占用最小化（< 100MB）
- ✅ 架构简洁
- ✅ 启动速度快
- ⚠️ 需要 Rust 开发能力
- ⚠️ 前端开发者需要适应 IPC 调用模式

## ADR-006: Pipeline 关键节点采用 Human-in-the-Loop

**日期:** 2026-08-07  
**状态:** ✅ 已接受

### 背景

PM Pipeline 生成 PRD、原型、代码等关键产物，需要人工确认确保质量。

### 决策

在以下节点设置 interrupt 暂停点：
1. **需求确认** — 确认需求范围、优先级
2. **PRD 审批** — 审查 PRD 内容，批准/拒绝/修改
3. **原型评审** — 查看原型，提出修改意见
4. **代码审查** — Code Review，接受/拒绝
5. **测试确认** — 确认测试覆盖度

### 理由

1. **质量保证** — AI 生成的内容需要人工把关
2. **可控性** — 产品经理保持对产出的控制权
3. **学习曲线** — 通过审批过程，PM 可以学习 AI 的思路
4. **信任建立** — 逐步建立对 AI 能力的信任

### 后果

- ✅ 产出质量有保障
- ✅ PM 保持控制权
- ⚠️ 需要设计 HITL 交互 UI
- ⚠️ 需要实现检查点恢复机制

## ADR-007: 采用 SQLite 作为持久化方案

**日期:** 2026-08-07  
**状态:** ✅ 已接受

### 背景

Pipeline 状态、检查点、对话历史等需要持久化存储。

### 决策

选择 **SQLite** 作为主要持久化方案。

### 理由

1. **GraphFlow 内置** — SqliteSaver 直接可用
2. **成熟稳定** — 经过大量生产验证
3. **零配置** — 无需独立数据库服务
4. **本地存储** — 符合数据主权要求

### 后果

- ✅ 检查点持久化简单
- ✅ 本地存储，数据安全
- ⚠️ 不支持多用户/云同步（未来如需，可切换到 PostgreSQL）

## ADR-008: HITL 交互采用内嵌式审批卡片 + 侧边通知

**日期:** 2026-08-07  
**状态:** ✅ 已接受

### 背景

需要设计前端 HITL 交互模式，展示审批内容并收集人工决策。

### 候选方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| 内嵌式审批卡片 | 上下文清晰 | 可能打断工作流 |
| 侧边通知面板 | 不打断主工作区 | 可能错过通知 |
| 模态对话框 | 强制关注 | 过于强势 |
| 独立审批页面 | 专注审批 | 跳转成本高 |

### 决策

采用**内嵌式审批卡片 + 侧边通知**组合方案：
- **内嵌式审批卡片** — 在 RndCenterView 中直接展示审批内容
- **侧边通知面板** — 显示待审批项列表，可折叠

### 理由

1. **上下文清晰** — 审批内容与工作区在同一视图
2. **不打断** — 侧边通知可折叠，不强制打断
3. **快速响应** — 直接在内嵌卡片中操作
4. **多任务** — 侧边面板可显示多个待审批项

### 后果

- ✅ 用户体验流畅
- ✅ 上下文保持清晰
- ⚠️ 需要设计复杂的 UI 组件
